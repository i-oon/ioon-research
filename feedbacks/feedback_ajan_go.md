### **Meeting Summary: Ajan Go, Ioon (Week 4)**

**Topic Focus: Cross-Morphology Transfer ด้วย Latent Action World Models**
ไออุ่นนำเสนอแนวคิดการแก้ปัญหาเรื่อง Reinforcement Learning (RL) ที่มักจะยึดติดกับรูปร่างของหุ่นยนต์ (Specific Morphology) โดยเสนอการใช้ **World Model** เข้ามาช่วยหา "ภาษากลาง" หรือ **Latent Action Space** เพื่อให้หุ่นยนต์ที่รูปร่างต่างกันสามารถแชร์ทักษะการเดินร่วมกันได้.

**1. เปเปอร์อ้างอิงและแนวคิดหลัก (Core Concepts)**
*   **Dreamer Model:** โมเดลที่ใช้จัดการกับวิดีโอเฟรม เพื่อหาสเปซร่วมกัน ทำให้สามารถทำนาย (Predict) อนาคตได้ล่วงหน้า ช่วยลดเวลาในการสุ่มพฤติกรรม (Computation Efficiency).
*   **Action Robot Foundation World Model:** การนำ Latent Action Space มาใช้รวมศูนย์ (Unify) ระหว่างแขนกล (Manipulators) หลายๆ รูปแบบ ซึ่งไออุ่นต้องการนำแนวคิดนี้มาประยุกต์ใช้กับ **หุ่นยนต์เดิน (Locomotion)** ซึ่งยังไม่มีใครทำ.

**2. โครงสร้างไปป์ไลน์ที่นำเสนอ (Proposed Pipeline)** แบ่งเป็น 2 เฟส:
*   **Phase 1: Pretraining (การสร้าง World Model)** 
    *   โมเดลจะเรียนรู้จากภาพเฟรมวิดีโอ (Observation) และ Action เพื่อสร้างโมเดลก้อนย่อย 2 ตัวคือ:
        1.  *Inverse Dynamic Model (IDM):* ทำหน้าที่แปลงความสัมพันธ์ระหว่างเฟรมให้กลายเป็นภาษากลาง (Latent Action).
        2.  *Forward Dynamic Model (FDM):* นำ Latent Action ไปทำนายสถานะในอนาคต (Next State).
*   **Phase 2: Policy Training**
    *   นำ FDM ที่เทรนเสร็จแล้ว มาช่วยบอก Next State และประเมิน Expected Reward ให้กับระบบ Actor-Critic.
    *   ใช้ **Action Projector** เพื่อแปลภาษากลาง (Latent Space) กลับไปเป็นคำสั่งข้อต่อ (Joint Command) ให้หุ่นยนต์แต่ละตัวนำไปใช้งานจริง.

**3. ข้อถกเถียงและปัญหาหลักที่พบจากการระดมสมอง (Debate & Challenges)**
*   **ปัญหาคอขวดที่ "Action Projector":** อาจารย์และรุ่นพี่ (พี่นาย/พี่แฮป) ตั้งคำถามหนักมากในจุดนี้ ว่าถ้าสุดท้ายแล้ว Policy และหุ่นยนต์ต้องการคำสั่งแบบ "Joint Space" (องศาข้อต่อ) ทำไมเราถึงต้องแปลงไปเป็น "Latent Space / Frame Space" ให้ซับซ้อนแล้วต้องมีตัวแปลงกลับอีกรอบ?. 
*   **ความยากของข้อมูลวิดีโอสัตว์จริง:** การไปหาวิดีโอสุนัขหรือแมลงจริงๆ มาหาค่า Action Space ที่แท้จริงเพื่อใช้เป็น Data นั้นทำได้ยากมาก และอาจจะใช้เทียบกับข้อต่อหุ่นยนต์ตรงๆ ไม่ได้.

**4. ข้อสรุปและแผนการปรับแก้ (Conclusion & Pivot Strategy)**
เพื่อเป็นการพิสูจน์คอนเซปต์ (Prove Concept) ในเบื้องต้นโดยไม่ต้องเจอปัญหาทางเทคนิคที่ซับซ้อนเกินไป อาจารย์และทีมงานจึงแนะนำให้ปรับลดสโคป (Simplify) ดังนี้:
*   **ทำทุกอย่างใน Simulation เท่านั้น:** เปลี่ยนจากการใช้วิดีโอสัตว์จริง มาเป็นการสร้างหุ่นยนต์ในซิมูเลชันแทน.
*   **สร้างโมเดลแมลง (Stick Insect) 3 รูปแบบ:** ให้ลองสร้างหุ่นยนต์แมลงที่มีความยาวขาต่างกันในซิมูเลชัน เช่น ขาสั้น, ขากลาง, และขายาว.
*   **วิธีทดสอบ (Validation):** 
    1. ให้ทำการเก็บข้อมูล (Data Collection) ท่าเดินจากแมลง **ขาสั้น** และ **ขายาว** นำไปเทรนเข้า World Model ใน Phase 1.
    2. นำ World Model ที่ได้ ไปทำนายและพยายามทำให้แมลง **ขากลาง** (ตัวที่ไม่เคยเห็นมาก่อน) สามารถเดินได้.
    3. นำ Latent Action ที่ได้มาทำ PCA ดูว่า Action จากหุ่นยนต์ที่ขาสั้นและยาว เกาะกลุ่ม (Cluster) ร่วมกันเป็นพฤติกรรมเดียวกันหรือไม่ เพื่อวัดผลว่าโมเดลเข้าใจภาษากลางจริงๆ.

**5. งานที่ต้องทำต่อไป (Action Items / Homework)**
*   ไออุ่นต้องกลับไปเขียนแผนภาพ (Pipeline Diagram) ของ **Phase 1** ให้ชัดเจนว่า Input และ Output คืออะไรกันแน่ และจะมีวิธีการสร้าง (Generate) รวมถึงการวัดผล (Measure) ข้อมูลเซ็ตนี้อย่างไร.

### **Week 5 Progress Update: Ioon (Cross-Morphology Transfer)**

**1. การปรับจูน Pipeline และโครงสร้างระบบ (System Architecture)**
*   **เปลี่ยนชื่อบล็อกเพื่อความเข้าใจที่ถูกต้อง:** เปลี่ยนชื่อจาก Inverse Dynamic Model เป็น **"Inverse Transition Model"** เพื่อป้องกันความเข้าใจผิด (Misleading) ว่ามันเกี่ยวข้องกับการคำนวณแรงทางฟิสิกส์ (Dynamics) ทั้งที่จริงมันแค่ทำงานกับข้อมูลภาพ
*   **กระบวนการทำงานของ Phase 1:**
    1.  รับข้อมูลภาพจาก **Camera Sensor (Third-person view)** และล็อกคำสั่งข้อต่อ (Joint command)
    2.  ส่งภาพเข้า **Visual Encoder** เพื่อสกัดออกมาเป็นตัวแปรฟีเจอร์ (Feature) โดยไออุ่นจะดึง Pre-trained model สำเร็จรูปที่เคยถูกเทรนด้วยรูปและวิดีโอทั่วไปกว่า 1 ล้านภาพมาประยุกต์ใช้งานเลย
    3.  ส่งฟีเจอร์เข้า **Inverse Transition Model** ซึ่งใช้กลไก **Attention Mechanism** ในการหาความสัมพันธ์ระหว่างเฟรม (State ปัจจุบันกับ State ถัดไป) เพื่อสกัดออกมาเป็น "ภาษากลาง" (Latent Action)
    4.  นำ Latent Action ไปทำนาย Feature ใน Time step ถัดไป (วนลูป) จนได้ World Model

**2. ขอบเขตการทดสอบและการตั้งค่า (Setup & Scope)**

*   **ใช้รูปภาพช่วยเล่าเรื่อง:** ควรเพิ่มรูปภาพของหุ่นยนต์หลายๆ รูปแบบ (Morphologies) เพื่อชี้ให้กรรมการเห็นภาพทันทีว่า โครงสร้างที่ต่างกันทำให้เกิดปัญหาในการใช้ข้อมูลการเคลื่อนที่ร่วมกันอย่างไร
*   **ทำตารางเปรียบเทียบ (Comparison Table):** ให้ทำตารางเปรียบเทียบข้อจำกัดให้ชัดเจน ระหว่างงานวิจัยอื่นๆ (ที่ต้องพึ่งพา Proprioceptive feedback) กับงานของเรา (ที่ใช้เพียง Visual observation อย่างเดียว) เพื่อโชว์จุดแข็งของงาน

**3. ความชัดเจนของเป้าหมายและผลลัพธ์ (Outcome Clarity)**
*   **เน้นย้ำผลลัพธ์ปลายทาง:** พี่แฮปแนะนำให้สรุปในสไลด์ให้เคลียร์ว่า ผลลัพธ์สุดท้าย (Outcome) ของงานนี้คือการได้ **"Latent Action"** ซึ่งเปรียบเสมือนเป็น **"Unified Policy"** ที่จะนำไปขับเคลื่อนหุ่นยนต์รูปร่างต่างๆ (Cross-Morphology) ได้
*   **ต้องมีภาพ Validation Pipeline สรุปจบ:** อาจารย์โก้รีเควสต์ให้วาดไปป์ไลน์การทดสอบในตอนท้ายให้เป็นรูปธรรมว่า ภาพรวมการทำงานคืออะไร เช่น นำภาพ Snapshot ของแมลงขายาว -> เข้าโมเดลเพื่อสกัด Latent space -> แล้วถ่ายโอนไปให้ขากลางหรือขาสั้นเดินได้อย่างไร (แสดงให้เห็นว่าจะเทรนหรือไม่เทรนอย่างไร)

**4. ฟีดแบคเพื่อปรับแก้สไลด์แบบจุดต่อจุด (Specific Slide Corrections จากพี่นาย)**
*   **สไลด์ 17 (สมการตัวชี้วัดความสำเร็จ):** การเขียนสมการตัวอักษรว่า `Morphology decoder < Morphology decoder (Latent vs Raw)` ดูเข้าใจยากและสื่อสารไม่ชัดเจน พี่แฮปแนะนำให้เขียนสื่อสารไปตรงๆ เลยว่า **"Latent action จะต้องไม่ยึดติดกับ morphology ใดเป็นพิเศษ"** (อธิบายว่าตัวแปรของเราต้อง decode ออกมาเป็น morphology ใดๆ ได้น้อยที่สุด)
*   **สไลด์ 18-19 (สถาปัตยกรรม V-JEPA2):** ในช่วงที่อธิบายผลการตรวจสอบโมเดล JEPA ควรเอาแผนภาพสถาปัตยกรรม (Architecture) ของมันขึ้นมาโชว์ประกบด้วยเสมอ เพราะโครงสร้างมันใหญ่และซับซ้อน กรรมการอาจจะลืมไปแล้วว่าคุณกำลังพูดถึงการทดสอบบล็อกไหนของระบบอยู่



จากการประชุม **"ajan go (week 11).m4a"** ที่ไออุ่นได้นำเสนอผลการทดลองวิเคราะห์จุดบกพร่องและแนวทางการเพิ่ม **Cross-Body Loss** เพื่อแก้ปัญหาโมเดลจำรูปทรงหุ่นยนต์ (Memorization) นี่คือสรุปฟีดแบค ข้อเสนอแนะ และคำถามสำคัญทั้งหมดจากอาจารย์โก้และผู้เข้าร่วมประชุมอย่างละเอียด ซึ่งจำเป็นอย่างยิ่งสำหรับการเตรียมตัวตอบคำถามกรรมการท่านอื่นครับ:

### **1. การปรับปรุงแผนภาพสถาปัตยกรรมระบบ (Simplify System Architecture & Diagram)**
* **ปัญหา:** เนื่องจากระบบมีความซับซ้อนและมีท่อข้อมูลไหลเวียนหลายทิศทาง กรรมการหรือคนภายนอกที่ฟังครั้งแรกจะเข้าใจได้ยากมาก
* **ฟีดแบค/คำแนะนำ:** อาจารย์โก้แนะนำให้ **เขียนบล็อกไดอะแกรมที่ลดทอนความซับซ้อนลง (Simplify)** และ **ใช้รูปภาพประกอบเยอะๆ** 
* **จุดที่ต้องระบุให้ชัดเจนในภาพ:** 
  * แผนภาพควรแยกแยะชัดเจนว่าส่วนไหนคือโครงสร้างหลัก (Backbone)
  * ส่วนไหนที่แช่แข็งค่าพารามิเตอร์เอาไว้ (Frozen) 
  * และส่วนไหนคือ **"ตัวเชื่อมต่อ (Connector/Head)"** ที่ต้องนำมาไฟน์จูนเพิ่มในขั้นตอนที่ต้องการขยายผลลัพธ์ไปยังหุ่นยนต์รูปทรงอื่น (Cross-Morphology หรือ Cross-Embodiment) เพื่อให้เห็นภาพการควบคุมระบบได้ง่ายที่สุด

---

### **2. ข้อสงสัยเชิงลึกเกี่ยวกับการข้ามประเภทหุ่นยนต์ (Cross-Embodiment & Pattern Mapping)**
* **คำถามจี้จุดสำคัญ:** อาจารย์โก้ตั้งคำถามท้าทายว่า ในสภาวะที่สรีระและพฤติกรรมการเคลื่อนที่แตกต่างกันอย่างสิ้นเชิง เช่น แมลงสติ๊กอินเซกต์ (6 ขา / 18 มอเตอร์) เปรียบเทียบกับหมา B1 (4 ขา / 12 มอเตอร์) ซึ่งแพทเทิร์นของข้อต่อขยับคนละทางกันเลย **การใช้เพียง "Connector/Head" มาไฟน์จูนค่าเชื่อมต่อจาก Latent Space ไปยังขาของร่างใหม่ จะเพียงพอและสามารถประคับประคองให้เดินได้จริงหรือ?**
* **แนวทางการวิเคราะห์ต่อยอด:** 
  * ให้ลองวิเคราะห์ไปถึงกรณีประยุกต์ใช้ในอนาคต เช่น การควบคุมหมาที่พิการขาขาด (ขาลดลงจาก 6 ขา เหลือ 4 ขา)
  * หรือเคสของหุ่นยนต์ไฮบริดที่ผสมข้ามรูปร่าง (เช่น ขาคู่หน้าเป็นขาหมา B1 แต่ขาคู่หลังเป็นขาแมลง) ว่าระบบพยากรณ์จะสามารถปรับตัวทำงานควบคุมร่วมกันได้หรือไม่

---

### **3. ข้อจำกัดเชิงทัศนวิสัยและกล้อง (Camera Limits & Occlusion)**
* **คำถาม:** ปัจจุบันระบบใช้มุมมองกล้อง 2D ทะแยงมุมมองจากด้านบนเฉียงข้าง (Diagonal side-view) อาจารย์โก้และทีมงานตั้งคำถามเรื่อง **"ข้อจำกัดของมุมกล้องและปัญหาการบดบัง (Occlusion)"**
* **ประเด็นที่ต้องกังวล:** หากในอนาคตท่าทางการเอียงของบอดี้หุ่นยนต์บังขาอีกฝั่งจนมิด หรือมีพฤติกรรมก้าวเดินบางจังหวะที่หายไปจากภาพอย่างสิ้นเชิง โมเดลจะยังสามารถพยากรณ์ไดนามิกการเดินได้อย่างถูกต้องหรือไม่

---

### **4. ข้อถกเถียงเรื่องการกักขังพฤติกรรม (Emergent Property Constraint)**
* **ประเด็นถกเถียงเรื่อง Loss ฟังก์ชัน:** เพื่อแก้ไขปัญหาโมเดลจำสรีระหุ่นเก่า ไออุ่นได้ใส่ **Cross-Body Loss** สลับภาพหุ่นกับแอคชันเพื่อบังคับให้โมเดลหันมาใส่ใจภาพตรงหน้ามากขึ้น
* **ฟีดแบคสำคัญ:** อาจารย์โก้ตั้งข้อสังเกตเชิงลึกว่า การเพิ่มข้อจำกัด (Constraint) ตรงนี้เข้าไป **จะเป็นการไปจำกัดพฤติกรรมแปลกใหม่ที่ควรจะเกิดขึ้นเองตามธรรมชาติของโมเดล (Emergent Property) หรือไม่?** 
* **คำอธิบาย:** การบีบโมเดลจนตึงเกินไป อาจทำให้ความหลากหลาย (Diversity) หรือความยืดหยุ่นแปลกใหม่ที่ Latent Action Space เคยมี ดร็อปลงไปอย่างน่าเสียดาย จึงต้องบาลานซ์ค่าน้ำหนักตรงนี้ให้ดี แต่พอบอกว่าพฤติกรรมต้องแมพให้ถูกต้องตามร่างกายที่เห็นก็เข้าใจดี

---

### **5. การดีไซน์เกณฑ์ประเมินประสิทธิภาพของ Action (Action Evaluation Metric)**
* **คำถาม:** ในเปเปอร์อ้างอิง (เช่น LAC World Model) เขาใช้เกณฑ์อะไรในการวัดว่า Action ที่ได้ออกมาทำงานได้ดีหรือไม่ดี
* **ฟีดแบค:** ไออุ่นชี้แจงว่าเปเปอร์เดิมวัดผลน้อยมาก โดยพล็อตเพียง t-SNE map / umap เพื่อดูการเกาะกลุ่ม (Clustering) ของเวกเตอร์แอคชันเท่านั้น 
* **คำแนะนำ:** อาจารย์โก้แนะนำให้ไออุ่น **"ดีไซน์และคิดค้นเกณฑ์การวัดผล (Metric) หรือลักษณะการพล็อตกราฟ/รูปภาพเพื่อประเมินความสำเร็จของ Action ขึ้นมาใหม่ด้วยตัวเองเลย"** เพื่อให้เห็นผลต่างประสิทธิภาพเชิงพฤติกรรมการเคลื่อนที่ได้อย่างลึกซึ้งและชัดเจนกว่าเปเปอร์ดั้งเดิม

---

### **6. แผนงานระยะถัดไปและการเชื่อมโยงโปรเจกต์กลุ่ม (Next Steps & Lab Synthesis)**
* **สเต็ปถัดไปของโปรเจกต์:** ก่อนที่จะขยับไปสู่เฟสถัดไป ต้องดีบั๊กและตรวจสอบสัดส่วนการไหลของข้อมูลในไปป์ไลน์ให้แน่ใจว่าถูกต้องตามหลักการ จากนั้น เป้าหมายหลักจริงๆ คือการนำก้อน Pre-trained World Model นี้ไปช่วยเร่งการฝึกสอน Policy ตั้งแต่ศูนย์ เพื่อตรวจสอบว่าสามารถช่วยลดระยะเวลาและประหยัดข้อมูลการลองผิดลองถูก (Sample Efficiency) ได้ดีกว่าการเริ่มรัน RL ทั่วไปอย่างไร
* **การรวมผลลัพธ์ของแล็บ (Big Picture):** อาจารย์โก้อยากเห็นภาพการเปรียบเทียบและการบูรณาการโปรเจกต์ของน้องๆ ทั้ง 3 คน (บีม - IRL, พราหมณ์ - Flow Matching, ไออุ่น - World Model) ออกมาเป็นคู่มือหรือตารางที่ชัดเจน เพื่อตอบโจทย์กลุ่มผู้ใช้งานภายนอก (End-user) ว่า **"หากพวกเขามีข้อมูลประเภทนี้อยู่ในมือ ควรเลือกใช้เฟรมเวิร์กของใครจึงจะคุ้มค่าและทรงประสิทธิภาพที่สุด"**

จากการประชุม Ajan Go (Week 12) 

ซึ่งเน้นไปที่การหารือเชิงลึกเกี่ยวกับความคืบหน้าของไออุ่น (Ioon) ในการแก้ไขไปป์ไลน์เพื่อเตรียมความพร้อมสำหรับ Phase 2 (Cross-Embodiment) ระหว่างหุ่นยนต์สติ๊กอินเซกต์ (Stick Insect - 6 ขา/18 ข้อต่อ) และหุ่นยนต์ B1 (4 ขา/12 ข้อต่อ) โดยสามารถสรุปฟีดแบค ข้อถกเถียงเชิงวิชาการ และคำแนะนำที่จำเป็นทั้งหมดแยกเป็นหัวข้อได้ดังนี้ครับ:
1. สรุปความคืบหน้าและการทดลองล่าสุด (Stage 2: Cross-Embodiment)
การทดสอบกับ Unseen Body ข้ามประเภท: เมื่อลองนำโมเดล Pre-training (Stage 1 ที่เคยเห็นแต่แมลง) ไปใช้ทำนายกับหุ่นยนต์ B1 ซึ่งมีสรีระต่างออกไปอย่างสิ้นเชิง พบว่าโมเดลล้มเหลวในการทำนายและกู้คืนคำสั่ง (Reconstruct) รวมถึงการพยากรณ์ Next State ใน World Model ก็ได้ผลลัพธ์ที่แย่มาก
เหตุผลเชิงระบบที่ Stage 2 ยากกว่า Stage 1:
ใน Stage 1 ดาต้าเซตทั้งหมดมาจาก Expert ตัวเดียวกันที่มีท่าทางและความตั้งใจแบบเดียวกัน (Single expert intention) จึงแมปข้ามความยาวขาแมลงได้ง่าย
ใน Stage 2 โครงสร้างข้อต่อและขนาดของสองหุ่นยนต์ไม่สอดคล้องกัน (Dimension Mismatch) รวมถึงไม่มี Behavior หรือความเร็วร่วมกันที่ชัดเจน ทำให้แมปข้อมูลกันตรงๆ แบบเดิมไม่ได้
2. ข้อถกเถียงและมุมมองหลัก: Joint Space vs. Task (Cartesian) Space
นี่เป็นข้อถกเถียงที่เข้มข้นที่สุดระหว่างไออุ่นและอาจารย์โก้เพื่อหาทางออกในการส่งคำสั่งของไปป์ไลน์:
มุมมองของไออุ่น (เสนอให้เปลี่ยนไปใช้ Cartesian Space): ไออุ่นตั้งสังเกตว่าเปเปอร์ต้นฉบับ (LAC World Model) ที่ทำข้ามบอดี้สำเร็จในงานแขนกล (Manipulation) นั้น เลือกให้ Target Action เป็น "ตำแหน่งปลายแขน (N-effector)" หรือ Cartesian Space เสมอ เพราะทุกหุ่นยนต์จะแชร์เป้าหมายเชิงพื้นที่เดียวกัน
 แต่โปรเจกต์นี้ดันเลือกใช้ Joint space (องศาข้อต่อ) ที่ผูกติดกับร่าง ซึ่งไออุ่นมองว่าผิดหลักโครงสร้างและเสนอให้ปรับเป้าหมายไปทำนายเป็นพิกเซลของเท้า (Foot Trajectory / Task Space) แทน
มุมมองและฟีดแบคของอาจารย์โก้ (ยังคงสนับสนุน Joint Space):
อาจารย์โก้เห็นต่างและระบุว่ายังคง ชอบและสนับสนุน Joint Space มากกว่า เพราะหากย้ายไปเล่นที่ Cartesian Space มันจะทำให้ระบบมีข้อจำกัดตรงที่ "เราจำเป็นต้องทราบ Kinematic Model (แบบจำลองจลนศาสตร์) และ Inverse Kinematics ของหุ่นยนต์เสมอ"
 ซึ่งหากนำไปประยุกต์ใช้กับหุ่นยนต์ชีวภาพหรือสรีระแปลกๆ ที่หา Kinematic Model ไม่ได้ ไปป์ไลน์นี้จะล้มทันที
เกณฑ์ชี้วัดความสำเร็จของ Joint Space: อาจารย์โก้ชี้แนะว่า แม้การแมปข้ามประเภทใน Joint Space จะไม่สมบูรณ์แบบ 100% แต่หากเรานำ World Model ที่ได้นี้ไปช่วยเป็น Initialization ในการเทรน RL (Fine-tune) แล้วมัน สามารถประหยัดเวลาฝึกสอนและเก็บตัวอย่าง (Sampling Efficiency) ได้ดีกว่าการเริ่มเทรน RL จากศูนย์ (from scratch) อย่างชัดเจน แค่นี้ก็ถือเป็นข้อพิสูจน์วิจัยที่ยอมรับได้และน่าสนใจมากแล้ว
3. เทคนิคที่ทดลองเพิ่มแล้วได้ผลลัพธ์ที่ดีขึ้น
ไออุ่นได้ลองปรับจูนการเทรนบางจุดและพบผลลัพธ์เชิงบวก ดังนี้:
การเพิ่มความหลากหลายของความเร็ว (Speed Variety): แต่เดิมใช้ข้อมูลเดินด้วยความเร็วคงที่สเต็ปเดียว แต่เมื่อลองใส่ช่วงความเร็วที่กว้างขึ้น (Varying Speed Range) พบว่าช่วยบังคับให้โมเดล Motion Decoder หันมา "มองและวิเคราะห์ภาพสรีระจริง" (Image Geometry) มากขึ้น แทนที่จะจดจำเฉพาะตัวแปร Latent Action เพียงอย่างเดียว ซึ่งเป็นแนวทางที่ถูกต้องสำหรับการทดสอบหุ่น unseen body
การใช้ "Body Head" และ Loss บังคับสปีดเป้าหมาย: สร้างบล็อกพยากรณ์ความเร็ว (Body Head) ของทั้งสองสรีระ และเพิ่ม Loss ฟังก์ชันเข้ามารีดแรงขับเคลื่อนในทรานซิชันที่สัมพันธ์กัน ช่วยให้ตัวเลข Reconstruction R-Square ที่เคยติดลบกู้คืนกลับมาเป็นค่าบวกและสามารถโอนถ่ายพฤติกรรม (Transfer) เริ่มได้ผลดีขึ้น
การทดสอบ Identity ใน Latent Action (Z): ไออุ่นลองถอดข้อมูลเชิงเปรียบเทียบประเภท Identity ของหุ่นออกจาก Latent Action พบว่าไม่ได้ช่วยปรับปรุงหรือทำให้เกิดความต่างเชิงพฤติกรรมอย่างมีนัยสำคัญ
4. ปัญหาพฤติกรรมดาต้าน้อยเกินไป และทางแก้ "CPG Hack" จากอาจารย์โก้
ปัญหา: World Model และโมดูลเดาอนาคต (Forward Transition Model) มีพฤติกรรมค่อนข้างอยู่กับที่เพราะชุดข้อมูลจำกัดอยู่แค่การเดินตรงอย่างเดียว (Forward Walking only)
 ไออุ่นต้องการเพิ่มดาต้าพฤติกรรมอื่นๆ เช่น เดินถอยหลัง เลี้ยวซ้าย/ขวา และเดินข้าง แต่คิดหาคอนโทรลเลอร์หรือรัน Expert ท่าเดินเหล่านี้ได้ยาก
ทางแก้ "CPG Hack" ที่สะดวกรวดเร็ว: อาจารย์โก้ได้เสนอทางลัดในการเก็บข้อมูลพฤติกรรมเดินที่หลากหลายสำหรับหุ่นยนต์แมลง โดยการใช้ CPG (Central Pattern Generator) Controller (ซึ่งเป็นระบบสั่นสัญญาณคาบสำเร็จรูปของพี่โจ้ที่มีอยู่แล้วในแล็บ)
:
คูณสัญญาณเพื่อเปลี่ยนทิศทาง: เขียนโค้ดสั้นๆ เพียงไม่กี่บรรทัดเพื่อแปรพิกัดเดิน เช่น นำสัญญาณขยับข้อต่อมา คูณด้วย -1 เพื่อให้แมลงเดินถอยหลัง
หากต้องการให้เลี้ยวซ้าย/ขวา ให้ข้างหนึ่งคูณด้วย -1 อีกฝั่งคูณด้วย +1 และหากต้องการให้ปัดข้าง (Lateral) ก็ควบคุมการทำงานของแกนมอเตอร์ข้อต่อกลางให้บิดปูเดินข้าง
วิธีนี้จะช่วยให้ไออุ่นสามารถจำลองและอัดวิดีโอทรานซิชันหลากท่าทางใน Sim ออกมาป้อนดาต้าเซตให้ World Model ได้ทันทีโดยไม่ต้องไปพึ่งพา Inverse Kinematics หรือเทรน RL Expert ให้เหนื่อย
5. สิ่งที่ไออุ่นต้องทำต่อหลังการประชุม (Action Items)
ขอข้อมูลและระบบควบคุม CPG จากพี่โจ้: เพื่อนำมาสร้างพฤติกรรมเดินหน้า ถอยหลัง เลี้ยว และเดินข้างของ Stick Insect และเตรียมเก็บข้อมูล SNAPSHOT วิดีโอหลายๆ ท่าทาง
ปรับปรุงความหนาแน่นและสัดส่วนความหลากหลายในดาต้าเซต: เพื่อดึงศักยภาพของ Forward Transition Model ในการเรียนรู้และพยากรณ์ Next State ให้ R-Square ดีขึ้นกว่าปัจจุบัน
ออกแบบการทดสอบ Connector/Head เพิ่มเติม: วิเคราะห์ต่อว่าเมื่อดาต้าหลากหลายขึ้น ท่อเชื่อมสเปซข้ามขนาด (12 ไป 18 มอเตอร์) จะช่วยประหยัด Sampling Rate ในกระบวนการ RL ปลายทางได้ตามเป้าหมายของทีมวิจัยหรือไม่




จากการประชุม **p’hap (week 13).m4a** ซึ่งไออุ่นได้นำเสนอความคืบหน้าของ Stage 2 (Cross-Embodiment ระหว่าง Stick Insect และ B1) และแนวทางการใช้ Policy เพื่อสร้าง Candidate Action ให้ World Model เลือก นี่คือสรุปฟีดแบค ข้อติติง และข้อเสนอแนะที่สำคัญทั้งหมดจากพี่แฮป (และพี่นาย) ครับ:

**1. ข้อติติงเรื่องตรรกะของการใช้ Policy สร้าง Candidate Action**
*   **ทำไมต้องใช้ World Model มาเลือกอีก?** พี่แฮปตั้งคำถามเชิงตรรกะว่า หากไออุ่นจะเทรน Policy ขึ้นมาเพื่อทำหน้าที่พ่น Candidate Actions ออกมาให้ World Model เลือก ถ้า Policy นั้นมันเก่งอยู่แล้ว (เป็น Expert) มันก็ควรจะคาย Action ที่ดีที่สุดออกมาได้เลย ทำไมเราถึงยังต้องเอา World Model มานั่งให้คะแนน (Score) เพื่อเลือกช้อยส์รอบๆ อีก?
*   **ความหลากหลายของ Candidate มาจากไหน?** พี่แฮปสงสัยว่า Policy ปกติมันเป็น Fixed Network หากรับ State เดิมเข้าไป มันก็ต้องคาย Action เดิมออกมา แล้วเราจะสร้าง Candidate หลายๆ ตัวเลือกจาก Policy ได้อย่างไร? (จะใช้วิธีแอด Noise เข้าไปที่ปลายทางเพื่อสร้างตัวเลือก 10 ช้อยส์ให้ World Model เลือก หรือจะทำอย่างไร ต้องหาคำตอบให้ชัดเจน)
*   **ปัญหาคอขวด (Bottleneck):** พี่แฮปเตือนว่า หากใช้วิธีสร้าง Policy ขึ้นมาก่อนเพื่อพ่น Candidate มันจะกลายเป็นว่าเราต้องไปเหนื่อยเทรน Policy สำหรับแต่ละ Morphology ให้เก่งก่อนนำมาใช้งานหรือไม่ ซึ่งจะกลายเป็นข้อจำกัดและคอขวดของระบบนี้

**2. ฟีดแบคเรื่องระยะเวลาการทำนาย (Horizon Length)**
*   พี่แฮปตั้งคำถามเรื่องการให้คะแนน Candidate ว่า ระบบจำเป็นต้องทำนายไปจนจบ Episode (Full Rollout) เลยหรือไม่ถึงจะรู้ว่า Action นั้นดี
*   เมื่อไออุ่นชี้แจงว่าในเปเปอร์ต้นฉบับพิจารณาแค่ช่วงเวลาสั้นๆ (Short Horizon) แบบทีละสเต็ป พี่แฮปเห็นด้วยและยืนยันว่า **นี่คือข้อดีของ World Model** เพราะถ้าเราต้องรอจนจบ Episode เพื่อหารีวอร์ด เราก็ไม่รู้จะมี World Model ไปทำไม การทำนายแบบทีละ 1-2 สเต็ปแล้วบอกได้เลยว่า Action นี้นำไปสู่ State ที่ถูกต้องหรือไม่ จึงเป็นแนวทางที่เหมาะสม

**3. ข้อเสนอแนะให้เลือกทิศทาง Pipeline ให้ชัดเจน (Dreamer vs. Candidate Scoring)**
พี่แฮปชี้ให้เห็นว่าตอนนี้ทิศทางของไออุ่นอยู่ตรงกลางระหว่าง 2 วิธีการทำงาน และแนะนำให้เลือกไปในทางที่ใช้พลังงานและตอบโจทย์ได้ดีที่สุด:
*   **เวย์แบบ Dreamer:** ใช้ World Model ในการ "จินตนาการ (Imagine)" ภาพอนาคต เพื่อสร้าง Imaginary Rollouts เอามาอัปเดต Actor-Critic ในการเทรน RL (ซึ่งช่วยลด Sample Complexity และเพิ่มความเร็วในการเทรน)
*   **เวย์แบบ VLA (Candidate Scoring):** ใช้ World Model เป็นแค่ "ตัวประเมินคะแนน" Action ที่ถูกโยนมาให้เลือก ซึ่งเวย์นี้จะต้องตอบให้ได้ชัดเจนว่าจะเอา Candidate จากไหน (โดยที่ไม่เหนื่อยหามาป้อน)

**4. การบ้านชิ้นสำคัญที่สุด: ย้ำเรื่อง Research Gap**
*   ในตอนท้าย พี่แฮปเน้นย้ำอย่างหนักว่า ไออุ่นจะต้องคอนเฟิร์มและตอบให้ได้ชัดเจนว่า **Research Gap ที่กำลังจะปิดคืออะไร?**
*   โมเดลและการออกแบบไปป์ไลน์ของเรา **แตกต่างจากงานวิจัยที่มีอยู่แล้วในปัจจุบันอย่างไร?** (เช่น ต่างจาก Original Paper ตรงไหน การที่เรานำมาใช้กับ Locomotion มีอะไรที่ต่างออกไป) ซึ่งเป็นจุดสำคัญที่สุดที่ต้องชัดเจนก่อนเดินหน้าต่อ


จากการนำเสนอรายงานความคืบหน้าของไออุ่นในสัปดาห์ที่ 14 (p’hap week 14) ซึ่งเน้นเรื่องการวินิจฉัยปัญหาของ World Model ที่ละเลยไม่ยอมใช้แอคชัน (Latent Action) ในการทำนายภาพอนาคตอันเนื่องมาจากปัญหา "Third-Person View Spoiler" และข้อเสนอที่จะเปลี่ยนไปใช้กล้องบุคคลที่หนึ่ง (First-Person View) พี่แฮปได้ให้ฟีดแบค ข้อสังเกต และคำถามสำคัญเพื่อนำไปปรับปรุงระบบดังนี้ครับ:

### **1. ข้อสงสัยเชิงทัศนวิสัยเกี่ยวกับมุมมองบุคคลที่หนึ่ง (First-Person View Intuition)**
*   **หุ่นยนต์จะรับรู้ร่างกายตัวเองอย่างไร:** เมื่อไออุ่นเสนอแนวทางการเปลี่ยนมาใช้กล้อง First-Person (Ego-centric) เพื่อปิดบังเฉลยภาพขาตัวเองที่สปอยล์คาบการเคลื่อนที่ในมุมมองบุคคลที่สาม **พี่แฮปตั้งคำถามเชิงฟิสิกส์ว่า แล้วหุ่นยนต์จะรับรู้ได้อย่างไรว่าตอนนี้ขาของตัวเองกำลังทำอะไรอยู่?** ในเมื่อระบบไม่สามารถมองเห็นโครงสร้างขาและร่างกายของตัวเองในเฟรมภาพได้อีกต่อไป
*   **ความหมายทางพฤติกรรมของการใช้กล้องหน้า:** พี่แฮปถามถึงกลไกเชิงพฤติกรรม (Intuition) ว่าข้อมูลที่สกัดจากกล้องข้างหน้าเพียงอย่างเดียวเพื่อนำมาแมปกับ Action นั้นมีความสมเหตุสมผลอย่างไร และระบบจะสามารถประเมินและเลือกตัวเลือก (Candidate Action) ที่ดีที่สุดเพื่อตอบสนองต่อสิ่งแวดล้อมที่เห็นผ่านภาพตรงหน้าได้อย่างไร

### **2. ข้อจำกัดด้านทรัพยากรคอมพิวเตอร์ในการปรับแต่งโมเดล (Computational Constraints)**
*   **ความต้องการทรัพยากรในการ Fine-tune Foundation Model:** พี่แฮปได้ทักท้วงเรื่องทรัพยากรระบบคอมพิวเตอร์ว่า ปกติแล้ว Foundation Model ขนาดใหญ่ (เช่น V-JEPA) จะต้องการทรัพยากรประมวลผลสูงมาก การที่จะนำโมเดลใหญ่ระดับนี้มาประยุกต์ใช้งานและทำการปรับแต่ง (Fine-tune) เพื่อเรียนรู้โครงสร้างใหม่ ๆ **จำเป็นต้องอาศัยเครื่องคอมพิวเตอร์และ GPU ที่มีขนาดใหญ่** พี่แฮปจึงตั้งข้อสังเกตว่าทรัพยากรประมวลผลที่ทีมงานมีอยู่นั้นเพียงพอที่จะสนับสนุนการทำตรงนี้หรือไม่ 

แก้ข่าว พี่แฮปคิดว่าเราไฟน์ทูนเอนโค้ดเดอร์เลยถาม*


### **3. คำแนะนำในการรันระบบทดสอบการเดินจริง (Base Walk Validation)**
*   **ทดสอบการเดินแบบ Single Morphology ให้รอดก่อน:** พี่แฮปชี้แนะว่าท้ายที่สุดแล้ว สิ่งที่เราต้องการได้จากปลายทางของกระบวนการทำงานคือ Action (คำสั่งควบคุมข้อต่อ) จึงแนะนำให้ไออุ่นลองนำไปป์ไลน์ที่ออกแบบไว้ทั้งหมดไปทดสอบวิ่งจริงใน Simulator เพื่อ**พิสูจน์ให้เห็นอย่างน้อยสักครั้งว่าระบบควบคุมเต็มลูปนี้สามารถประคองหุ่นยนต์ตัวเดิมให้เดินได้จริง** (โดยยังไม่ต้องทดสอบข้ามประเภทหุ่นยนต์) เพื่อเช็คพฤติกรรมของ Full System และเป็นการยืนยันประสิทธิภาพขั้นพื้นฐานที่รัดกุมก่อนขยายผลต่อ

### **4. ความถูกต้องเชิงตรรกะของการใช้ World Model สอนโมเดลลูก (Teacher-Student Rigor)**
*   **ทำไม World Model ถึงพ่นแค่ภาพ:** พี่แฮปซักถามเพื่อความเข้าใจเชิงโครงสร้างว่า เหตุใดตัวแปรของ World Model (Forward Model) ถึงเลือกที่จะพ่นค่าแสดงผลลัพธ์ออกมาเป็น "ภาพ (Frame)" แทนที่จะพ่นออกมาเป็นคำสั่งข้อต่อหรือค่าแรงบิด (Joint Position หรือ Torque) โดยตรง *(ซึ่งไออุ่นได้ชี้แจงว่าระบบใช้ Frame ในโลกจินตนาการมาคำนวณหาค่าความต่างแบบ Mean Square Error เทียบกับเป้าหมายเพื่อเป็นตัวประเมินคุณค่าแทน)*
*   **ความพร้อมและการทำหน้าที่ของตัว Teacher:** พี่แฮปตั้งข้อสังเกตเชิงตรรกะว่า หากภาพอนาคตที่ World Model (Teacher) คาดการณ์ออกมานั้นยังมีประสิทธิภาพการทำนายในระยะยาวที่ไม่แม่นยำหรือไม่ดีพอ มันก็ยังไม่พร้อมและไม่ควรที่จะถูกเอาไปทำหน้าที่เป็นครูคอยประเมินหรือตัดสินว่า Candidate Action ของ Student ตัวไหนดีหรือไม่ดี

### **5. ความต่างเชิงมิติของเป้าหมายควบคุม (Joint Space vs. Cartesian Space)**
*   **ความท้าทายในระดับข้อต่อที่ไม่มีเป้าหมายร่วม:** พี่แฮปวิเคราะห์เชิงเปรียบเทียบว่า ในงานวิจัยอื่น (เช่น งานแขนกล/Manipulation) มักจะกำหนด Action ปลายทางให้อยู่ใน Cartesian Space (พิกัดตำแหน่งปลายขาหรือปลายแขน) ซึ่งทุก ๆ บอดี้จะแชร์เป้าหมายเชิงพื้นที่เดียวกันทำให้แมปข้ามร่างได้ง่าย แต่ระบบของไออุ่นเลือกทำนายในมิติ Joint Space (องศาข้อต่อ) โดยตรง ซึ่งไม่มีมิติอ้างอิงร่วมกัน ทำให้เชื่อมโยงสรีระและทดสอบควบคุมข้ามร่างได้ยากกว่ามาก

### **6. การขอร่วมดีบั๊กและตรวจสอบโค้ด (Action Items for Debugging)**
*   **ร่วมรีวิวฟังก์ชัน Objective ของ Pre-training:** พี่แฮปได้ขอให้ไออุ่นส่งลิงก์ Git Repository และไฟล์สไลด์นำเสนอมาให้หลังการประชุม เพื่อที่พี่แฮปจะเอาไปช่วยเปิดดูโค้ดการทำงานลึก ๆ และตรวจสอบว่าสมการ Objective / Loss ฟังก์ชันที่ใช้ในฝั่ง Pre-training ตอนนี้ใส่เงื่อนไขอะไรเอาไว้บ้าง เพื่อที่จะได้ช่วยวิเคราะห์หาสาเหตุและแก้ไขระบบร่วมกันต่อไปครับ
